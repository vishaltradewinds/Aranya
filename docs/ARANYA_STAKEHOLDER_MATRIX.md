# ARANYA Stakeholder Universe and Network Matrix

## Purpose

This is the first **stakeholder identification contract** for ARANYA.

It is deliberately a **working ecosystem map**, not a registration form, product menu or frozen taxonomy.

The objective is to identify who participates in the nature-based economy, what each node has and needs, what it can do, which networks it belongs to, what authority it legitimately holds, what evidence it creates or requires, and how ARANYA can connect it to real work.

## Core model

ARANYA is one common environment:

**STAKEHOLDER / NETWORK A ↔ ARANYA ↔ STAKEHOLDER / NETWORK B**

The stakeholder does not need to learn ARANYA's internal taxonomy. AI and orchestration should infer the relevant path from the stakeholder's intent, context, authority and evidence.

## Universal stakeholder expression

Every stakeholder or network should be able to express:

- **I HAVE** — resource, product, knowledge, infrastructure, capital, capacity or data.
- **I NEED** — material, market, finance, technology, service, people, certification or logistics.
- **I CAN** — produce, process, transport, research, train, test, certify, finance, aggregate or provide a service.
- **I WANT TO CONNECT** — with a relevant person, network, institution, market or capability.

## Authority model

Authority is not a status badge.

ARANYA should distinguish at minimum:

1. **Statutory authority** — authority created by law/regulation.
2. **Delegated/program authority** — authority explicitly delegated or granted within a programme or institution.
3. **Organisational authority** — authority to act for an organisation/network.
4. **Contractual authority** — authority arising from a valid agreement.
5. **Individual agency** — the person's own ability to act or provide information.
6. **Platform permission** — permission to use an ARANYA function; this does **not** create external legal authority.

The system must preserve **scope + jurisdiction + validity + source** for authority claims.

## Evidence model

Evidence should be attached to real work rather than generated as a separate reporting burden.

Typical evidence classes:

- identity / organisation
- resource origin
- rights / permissions
- quantity / weight
- location / time
- quality / test
- custody / movement
- processing / batch
- order / contract
- inspection / acceptance
- payment / settlement
- research / observation
- consent / provenance / benefit-sharing where applicable
- regulatory approval or decision

## Network topology

ARANYA should model relationships, not just users.

Examples:

- Community ↔ FPO/FPC
- FPO/FPC ↔ Buyer
- Producer ↔ Processor
- Processor ↔ Testing
- Producer ↔ Logistics
- Research ↔ Community
- Technology ↔ Enterprise
- Finance ↔ Producer network
- Certification ↔ Market
- Government programme ↔ Community network
- Biodiversity institution ↔ Community
- Restoration project ↔ Finance / buyer / verification

A stakeholder can belong to multiple networks. A network can connect to multiple networks. The graph must therefore support many-to-many relationships without forcing every participant into one organisation.

## Onboarding routes

Do not create one universal registration workflow.

Use five entry routes:

1. **Self** — stakeholder enters directly.
2. **Assisted** — field facilitator/CSC/partner helps.
3. **Network** — an existing network onboards its members progressively.
4. **Enterprise / institution** — organisation joins with its own users, capabilities and permissions.
5. **System / API** — an existing platform connects through an integration.

Registration is only an identity event. Successful onboarding requires useful participation:

**IDENTITY → CONTEXT → FIRST CONNECTION → REAL WORK → EVIDENCE → OUTCOME**

## ARANYA role by stakeholder

For each journey, ARANYA should classify its role as one or more of:

- **DISCOVER** — find a relevant person, network, resource or capability.
- **UNDERSTAND** — interpret intent, context, requirements and available paths.
- **ROUTE** — connect the right parties or systems.
- **ORCHESTRATE** — coordinate multi-party work.
- **EVIDENCE** — capture/protect provenance and work evidence.
- **VERIFY** — support verification without impersonating an authority.
- **TRANSACT** — support legitimate handover/order/settlement workflows.
- **AUDIT** — preserve history and traceability.
- **INFORM** — explain applicable requirements or available options.
- **INTEGRATE** — connect existing systems and networks.

ARANYA should **never silently become the authority** simply because it coordinates a journey.

## First implementation rule

This matrix is intentionally broad. Before national taxonomy, modules or dashboards are frozen, ARANYA should test the matrix against real journeys and identify:

- existing rail → integrate
- partial capability → interoperate and fill the gap
- fragmented capability → provide common connectivity
- missing infrastructure → evaluate as ARANYA infrastructure
- statutory function → integrate, never replace

## Success test

The matrix is useful only if it can answer, for a real stakeholder:

> **Who are you? What do you have? What do you need? What can you do? Who can you legitimately connect with? What authority applies? What evidence is required? What is the next real-world action? What outcome proves completion?**

If it cannot answer those questions, the stakeholder model is incomplete.
